# Правила проекта

## Назначение

Это публичное тестовое задание: сервис расчёта координат космических аппаратов.
Разработка локальная. Публикацию на GitHub выполняет владелец репозитория.
Исходное задание и рабочий план остаются локальными материалами: в коммиты их не включать.
Их возможную публикацию в конце работы решает владелец.

## Работа с владельцем

- Отвечать по-русски. Код, комментарии, docstrings и сообщения коммитов писать по-английски.
- Реализовывать только текущую согласованную версию. После её проверки, коммитов и тега остановиться для обсуждения.
- До изменения неоднозначного контракта объяснить варианты, последствия и предложенное решение.
- Объяснять предметную область простыми словами; при первом употреблении расшифровывать сокращения.
- Не добавлять инфраструктуру, зависимости, настройки и абстракции без используемого сценария.
- Перед коммитом назвать состав изменений и выполненные проверки.
- Публикуемая документация должна быть самодостаточной и не ссылаться на локальные материалы.

## Архитектура

- Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2 с asyncpg, PostgreSQL.
- `api/router` содержит HTTP-контракт; `api/managers` координирует операции;
  `api/db` содержит SQL; `api/services` управляет инфраструктурными ресурсами.
- `models/pydantic`, `models/sqlalchemy`, `models/enum`, `models/exceptions` содержат соответствующие модели.
  Каталоги создаются по мере появления кода.
- Вычислительное ядро не зависит от HTTP и PostgreSQL.
- `Services` владеет ресурсами приложения. Запуск и остановка проходят через FastAPI lifespan.
- `database.session()` владеет транзакцией: успешный выход фиксирует изменения, исключение откатывает.
  Связанные DB-операции используют одну переданную сессию. Во время CPU-расчёта транзакция не удерживается.
- Бизнес-данные передаются типизированными моделями. Не вводить универсальные контейнеры из `dict[str, Any]`.
- Использовать открытые зависимости. Корпоративные библиотеки, их исходный код и конфигурацию не переносить.

## Настройки и качество

- Все эксплуатационные настройки доступны через переменные окружения с префиксом `APP_`.
- Использовать группы `APP_DB_*`, `APP_TEST_DB_*`, а позднее `APP_COMPUTE_*`.
- Указывать единицы в именах: `_SEC`, `_MS`, `_BYTES`. Настройки описывать через Pydantic `Field`.
- Новая настройка должна использоваться кодом и отражаться в `.env.example`, Compose и документации.
- Poetry и `poetry.lock` фиксируют зависимости. Ruff отвечает за lint/format, ty за типизацию.
- Тесты добавлять вместе с поведением. Интеграционные тесты работают только с отдельной тестовой PostgreSQL.
- Alembic использует ORM metadata. После публикации миграции не переписывать: создавать новую.
- `main` содержит проверенные этапы. Возможности разрабатывать в `feat/*`, исправления в `fix/*`.
- Сохранять смысловые коммиты и merge-коммиты; версии отмечать тегами `vX.Y.Z`.
