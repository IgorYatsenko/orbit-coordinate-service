# Доступ и ограничения 1.1.0

## Как пользоваться

Настройки копируются командой `cp .env.example .env`, окружение запускается через
`docker compose up --build --wait`. Файл `.env` исключён из Git и Docker build context.
Пример содержит фиксированный ключ подписи для демонстрации;
`APP_AUTH_TOKEN_SECRET` позволяет задать собственный.

Для демонстрации достаточно одного заранее подготовленного пользователя:
**`testuser / test-password`**. После запуска окружения выполните:

```bash
docker compose exec app python -m api.demo_user
```

Функция в `api/demo_user.py` хеширует пароль и сохраняет запись
через `Services.database.session()`. Для локальной разработки та же функция доступна
как `poetry run poe add-test-user`. Повторный запуск сохраняет существующий UUID,
хеш пароля и состояние пользователя через `INSERT ... ON CONFLICT DO NOTHING`.
Логин: 3–64 ASCII-символа, первый символ буква или цифра, далее также `_`, `.`, `-`.
Пробелы по краям убираются, регистр приводится к нижнему. Пароль: 1–128 символов,
пробелы и регистр сохраняются. Отдельного интерфейса администрирования пользователей нет.

В Swagger выполните `POST /api/v1/auth/login`:

```json
{"username":"testuser","password":"test-password"}
```

Ответ содержит `access_token`, `token_type: "bearer"`, `expires_in: 900`.
В **Authorize** вставьте только токен. В HTTP он передаётся заголовком
`Authorization: Bearer <token>`. `GET /api/v1/auth/me` показывает текущего пользователя.
После истечения срока выполните вход повторно. Ответ входа запрещает кеширование.
Swagger сохраняет авторизацию только в текущем состоянии страницы.

Расчёт и весь реестр требуют токен. Health API и документация остаются открытыми:
health нужен инфраструктуре без пользовательских учётных данных, документация нужна для демонстрации.
`APP_DOCS_ENABLED=false` отключает Swagger и OpenAPI. Открытой регистрации и управления
чужими пользователями через HTTP нет. Все включённые пользователи имеют одинаковые права
на общий реестр. Владельцы записей, роли и отдельные организации в текущий контракт не входят.

## Почему пароль и короткий токен

Аутентификация отвечает на вопрос, кто обращается. Авторизация определяет разрешённые действия.
В этой версии аутентификация индивидуальная, а авторизация простая: активный пользователь
может выполнять бизнес-операции. API-ключи были альтернативой для межсервисного доступа,
но выбран пользовательский вход по логину и паролю.

Пароль проверяется при входе. После этого клиент предъявляет короткий временный токен,
чтобы не передавать пароль с каждым расчётом. JWT (JSON Web Token) содержит подписанные
поля: ID пользователя (`sub`), время выдачи (`iat`), окончание
срока (`exp`), издателя (`iss`) и получателя (`aud`). Пароля и персональных данных в нём нет.
Подпись HS256 использует HMAC с SHA-256: общий секрет позволяет серверу обнаружить изменение
содержимого. JWT можно прочитать, он не зашифрован. Алгоритм, issuer и audience проверяются явно.

15 минут ограничивают время использования потерянного токена без механизма постоянного продления.
Refresh-токен, то есть отдельный долгоживущий ключ продления, потребовал бы хранения сессий,
ротации и правил отзыва. Для прототипа достаточно повторного входа.
Удаление токена у клиента прекращает его использование этим клиентом, но не отзывает копии.

В каждом защищённом запросе сервер читает пользователя из PostgreSQL и проверяет
его существование и флаг активности. Удалённая или отключённая запись не получает доступ.
Отдельного счётчика отзыва токенов нет: демонстрационный сценарий не содержит
управления пользователями. Задача добавления тестового пользователя сохраняет его состояние.
Уже допущенный расчёт из-за этого не прерывается.
Смена секрета и перезапуск всех HTTP-процессов отзывает все токены.
Одинаковый секрет обязателен у всех экземпляров приложения; случайный ключ на каждый процесс
привёл бы к непредсказуемым отказам авторизации.

Непрозрачные случайные токены с серверными сессиями также подошли бы и упростили точечный отзыв.
JWT выбран как распространённый формат с явными сроком и назначением. При этом сервис
не объявляется полностью независимым от БД: проверка существования и активности требует чтения пользователя.
Отдельный сервер идентификации удобен для единого входа нескольких продуктов, но здесь
добавил бы самостоятельный сервис, настройку и сценарии отказа без требования единого входа.

Вход представляет собой собственный JSON-контракт и HTTP Bearer в Swagger.
Он не объявлен реализацией OAuth2 password grant. Для подключения внешнего провайдера входа
нужно отдельно согласовать протокол и перенести проверку личности на его сторону.

## Почему Argon2

Хеш пароля позволяет проверить совпадение, не храня исходный пароль.
Обычная быстрая хеш-функция подходит для контрольной суммы, но позволяет очень быстро
перебирать варианты пароля. Argon2id специально расходует время и память, усложняя перебор.
Библиотека `argon2-cffi` создаёт случайную соль и сохраняет её вместе с параметрами в строке хеша.
Одинаковые пароли не требуют одинаковых хешей. В БД есть только эта строка.

Начальные параметры: 64 MiB памяти, три прохода, две полосы обработки.
Это стартовая конфигурация; время входа нужно измерять на целевой машине.
Одновременно разрешены две проверки на HTTP-процесс: около 128 MiB рабочей памяти Argon2
плюс память Python и других компонентов. Параллельность ограничена отдельно от вычислений орбит.
Проверка выполняется в потоке, чтобы HTTP-процесс продолжал отвечать на другие запросы.
Отмена HTTP-ожидания не освобождает место, пока поток действительно не завершится.
При занятости двух мест возвращается `503 authentication_busy`, очередь не создаётся.

Для неизвестного логина выполняется проверка специального случайного хеша, созданного
при запуске. Сообщение об ошибке одинаково для неизвестного, отключённого пользователя
и неверного пароля. Это уменьшает различие во времени и содержимом ответа, но не является
доказательством абсолютно одинакового сетевого времени. Изменение параметров Argon2 влияет
на новые хеши; существующие продолжают проверяться по записанным в них параметрам.
Новый демонстрационный пользователь получает хеш с текущей конфигурацией.

## Почему Redis и как считается лимит

Rate limiter ограничивает частоту. Счётчик в памяти Python был бы отдельным у каждого
HTTP-процесса и обнулялся при его перезапуске. Redis даёт общий счётчик всем экземплярам,
без записи каждого запроса в основную БД. В текущей версии он не кеширует траектории.

Используется окно фиксированной продолжительности от первого запроса:

1. Redis увеличивает счётчик ключа; для нового ключа назначает срок удаления.
2. Lua-скрипт выполняет увеличение и назначение срока атомарно: конкурентный запрос
   не может вклиниться между этими командами.
3. До предела включительно запрос разрешён. Далее возвращается `429 rate_limit_exceeded`
   с `Retry-After`, целым числом секунд до окончания окна, округлённым вверх.
4. Отклонённые запросы увеличивают счётчик, но не продлевают окно. После удаления ключа
   следующий запрос открывает новое окно.

Начальные значения: 60 защищённых запросов за 60 секунд на ID пользователя;
10 попыток входа за 60 секунд на адрес клиента. Это два независимых счётчика.
Новый токен того же пользователя не даёт новую квоту. Расчёт, реестр и `/auth/me`
делят одну пользовательскую квоту. В неё входят допущенные к проверке пользователя запросы,
в том числе завершившиеся `404`, `422` и занятостью вычислителей `503`.
Невалидный или просроченный JWT отклоняется до обращения к Redis.
Лимит входа применяется до проверки пароля и валидации полей тела; синтаксически
сломанный JSON может быть отклонён самим FastAPI до вызова зависимости лимитера.

Простое окно допускает короткий всплеск на стыке двух окон, почти два лимита подряд.
Скользящее окно или алгоритм пополнения запаса запросов сгладили бы всплески, но усложнили
состояние и проверку. Здесь выбран минимальный явный механизм, а число одновременно
работающих тяжёлых задач дополнительно ограничивает вычислительный пул.
Предел 60 не обещает, что 60 тяжёлых расчётов завершатся за минуту.
`429` означает исчерпанную частоту пользователя; `503 compute_busy` означает занятые процессы.

Ключи имеют общий `APP_REDIS_KEY_PREFIX`, вид счётчика и SHA-256 от идентификатора.
Сырые IP не сохраняются в ключах. Это не делает короткое пространство IP криптографически анонимным.
Приложения, разделяющие квоту, используют одинаковые Redis DB, префикс и настройки лимита.
Разным окружениям нужны разные префиксы или экземпляры Redis.

При отказе Redis защищённые операции и вход возвращают `503 rate_limiter_unavailable`,
`ready` становится неуспешным, а `live` остаётся доступным. Обход лимита при сетевой ошибке
сделал бы защиту зависимой от отказа инфраструктуры. Общий deadline ограничивает Redis-команду,
включая повторные подключения клиента. Отказ PostgreSQL также блокирует проверку пользователя.

Счётчики временные: Compose отключает сохранение Redis на диск. Перезапуск Redis сбрасывает
окна; перезапуск только API их сохраняет. Лимит памяти Redis по умолчанию 64 MiB,
политика `noeviction` запрещает незаметное удаление счётчиков при нехватке памяти.
В таком случае команда Redis завершается ошибкой и доступ закрывается через `503`.
Redis в Compose один; высокая доступность инфраструктуры не реализована.

## Адрес клиента и граница локального запуска

По умолчанию сервер не доверяет `X-Forwarded-For`: иначе клиент мог бы менять заголовок
и обходить лимит входа. Для реального reverse proxy задаётся `APP_HTTP_TRUSTED_PROXY_IPS`
со списком его адресов или сетей. Символ `*` означает доверие всем и требует закрытого
прямого доступа к приложению. Пользователи за одним внешним IP делят лимит входа.

Compose публикует порты на loopback-интерфейсе локальной машины. Для внешнего развёртывания
пароль и Bearer-токен передаются только через HTTPS, а демонстрационные пароли БД и Redis
заменяются. Ограничитель приложения не ограничивает весь входящий трафик до HTTP-парсера;
защита сетевого периметра относится к конфигурации внешнего прокси.
