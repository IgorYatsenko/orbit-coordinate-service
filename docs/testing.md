# Проверки и начальные условия измерений

## Быстрые проверки

```bash
poetry run poe check
poetry run pre-commit run --all-files
```

`poe check` выполняет Ruff lint, проверку форматирования, ty с ошибкой на предупреждениях
и unit-тесты. Pre-commit дополнительно проверяет YAML/TOML, окончания файлов, конфликты
слияния, крупные файлы и признаки приватных ключей. Он сохраняет двойные пробелы,
используемые Markdown для переноса строки, включая исходный файл задания.

Все хуки запускаются через `poetry run`, поэтому используют версии из одного lock-файла.
После клонирования нужно выполнить `poetry install` и `poetry run pre-commit install`.
Изолированные окружения с отдельными версиями Ruff или ty не создаются.

## Unit-тесты

```bash
poetry run poe test-unit
```

Проверяются приоритеты `.env` и окружения, сокрытие и корректная передача пароля,
кэш конфигурации, отклонение некорректных лимитов, порядок запуска/остановки ресурсов,
очистка после частичного запуска, продолжение очистки при ошибке остановки,
HTTP-контракт живости/готовности, отключение OpenAPI, срок healthcheck и JSON-логи.

Тесты работают без БД. HTTP-запросы направляются в приложение через ASGI transport httpx;
ASGI (Asynchronous Server Gateway Interface) — интерфейс между Python-сервером и приложением.
В unit-тестах доступность БД заменяется контролируемым результатом.
Реальный запуск ресурсов проверяется следующим набором.

## Интеграционные тесты

Интеграционный тест проверяет взаимодействие нескольких реальных компонентов.
Здесь используются настоящие PostgreSQL, asyncpg, SQLAlchemy, Alembic и FastAPI lifespan.
SQL-запросы не заменяются mock-объектами.

Полностью в Docker:

```bash
docker compose --profile test run --build --rm tests
```

Или pytest в локальной `.venv`:

```bash
docker compose --profile test up -d --wait postgres-test
poetry run poe test-integration
```

Тесты используют только отдельный `postgres-test`. Его данные находятся в `tmpfs` — временном
хранилище в памяти — и исчезают после остановки контейнера. Рабочий volume не подключается.
Имя БД проверяется на суффикс `_test`, а реквизиты берутся исключительно из `APP_TEST_DB_*`.
В собственной конфигурации следует указывать выделенную тестовую БД: тесты создают и удаляют
служебную таблицу и выполняют откат миграций. Параллельные запуски на одной тестовой БД не предусмотрены.

| Сценарий | Что подтверждает |
| --- | --- |
| Upgrade → повторный upgrade → downgrade → upgrade | Миграции применимы, повторный запуск безопасен, исходная версия восстанавливается |
| `alembic check` | Применённая схема соответствует ORM metadata |
| Запрос готовности после lifespan | HTTP-обработчик действительно использует запущенную PostgreSQL |
| Успешная транзакция | Запись видна в следующей сессии после commit |
| Прикладная ошибка | Все записи операции откатываются |
| Нарушение уникальности | PostgreSQL отклоняет конфликт, транзакция откатывается, пул остаётся рабочим |
| Отмена асинхронной задачи | Незавершённая запись откатывается и соединение освобождается |
| Долгий SQL-запрос | Настроенный statement timeout срабатывает, после отката БД снова доступна |

Для последующей работы можно остановить только тестовый контейнер:

```bash
docker compose --profile test stop postgres-test
```

## Проверка контейнерного приложения

```bash
docker compose up --build --wait
curl --fail http://localhost:8000/health/ready
```

Эта проверка дополняет ASGI-тест: здесь используются собранный образ, настоящий HTTP-сервер,
TCP-соединение, сеть Compose и отдельный контейнер миграций.
При остановке PostgreSQL `/health/live` должен оставаться доступным, а `/health/ready`
должен вернуть 503 в пределах настроенного срока. После восстановления БД готовность должна восстановиться.

GitHub Actions повторяет проверки качества, интеграционные тесты и запуск Compose.
До push можно проверить конфигурацию и локальные эквиваленты; фактический запуск на GitHub произойдёт после публикации.

## С чего начинаются замеры

В 0.1.0 установлена исходная конфигурация: один HTTP-процесс, пять соединений в его DB-пуле,
ноль дополнительных соединений. Это начальные параметры, а не результат оптимизации.
Орбитальные бенчмарки появятся в 0.2.0 вместе с вычислительным ядром.

Первые входы: один КА, интервал один час и одни сутки, шаги 1 и 60 секунд.
Сначала измеряется один запрос, затем несколько одновременных запросов.
Для каждого опыта сохраняются исходные элементы, времена, версии, CPU/память Docker,
все влияющие переменные окружения и число повторов после прогрева.

Нужны полное время HTTP-ответа, время ядра, размер ответа, пик памяти,
доля отказов при перегрузке и задержка health API. Одно среднее значение может скрыть
редкие медленные запросы, поэтому сохраним медиану и p95 — время, быстрее которого завершились 95% запросов.
Доступность health API проверяется во время нагрузки, включая формирование большого JSON-ответа.

Затем меняется один параметр за опыт: число вычислительных процессов, число допущенных запросов
или размер входа. Начальный предел 100 000 точек сохраняется только если измерения подтвердят
приемлемые память и задержку. Изменение конфигурации документируется вместе с результатом.
До этих измерений численный SLA (Service Level Agreement — обязательство по уровню обслуживания)
для времени расчёта не заявляется.

## Проверка версии 0.1.0 — 20 октября 2026 года

- Ruff, ty и все pre-commit проверки прошли.
- Локально прошли 15 unit-тестов и 8 интеграционных тестов.
- В Linux-контейнере Python 3.13.14 прошли все 23 теста.
- Образы runtime/test собраны; PostgreSQL, мигратор и API запущены через Compose.
- Проверены HTTP 200 для live/ready, HTTP 503 для ready при остановленной БД и восстановление HTTP 200 после её запуска.
- Ответ ready при остановленной БД получен за 0.189 с. Это единичная проверка отказа, не бенчмарк производительности.
- GitHub Actions подготовлен; запуск на GitHub ожидает публикации репозитория.
