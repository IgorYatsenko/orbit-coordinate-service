# Проверки и начальные условия измерений

## Быстрые проверки

```bash
poetry run poe check
poetry run pre-commit run --all-files
```

`poe check` выполняет Ruff lint, проверку форматирования, ty с ошибкой на предупреждениях
и unit-тесты. Pre-commit дополнительно проверяет YAML/TOML, окончания файлов, конфликты
слияния, крупные файлы и признаки приватных ключей. Он сохраняет двойные пробелы,
используемые Markdown для переноса строки. Захваченные исходные файлы CelesTrak
исключены из исправления пробелов и окончания файла, чтобы сохранить байты и SHA-256 источника.

Все хуки запускаются через `poetry run`, поэтому используют версии из одного lock-файла.
После клонирования нужно выполнить `poetry install` и `poetry run pre-commit install`.
Изолированные окружения с отдельными версиями Ruff или ty не создаются.

## Unit-тесты

```bash
poetry run poe test-unit
```

Проверяются приоритеты `.env` и окружения, сокрытие и корректная передача пароля,
кэш конфигурации, отклонение некорректных лимитов, порядок запуска/остановки ресурсов,
очистка после частичного запуска, продолжение очистки при ошибке остановки,
HTTP-контракт живости/готовности, отключение OpenAPI, срок healthcheck и JSON-логи.

В 0.2.0 добавлены контракты времени и чисел, контрольная сумма TLE, невозможная эпоха,
контрольные векторы SGP4 для околоземного и дальнего аппарата, в том числе до эпохи,
проверка WGS84 через прямую формулу эллипсоида, сравнение TLE/JSON, NaN/Inf,
девятизначный NORAD ID, ошибка орбиты и точное сохранение эпохи.
Управляемые Future проверяют перегрузку, отмену и тайм-аут с удержанием места,
смерть вычислителя и ограничение числа одновременных health-проб.

Тесты работают без БД. HTTP-запросы направляются в приложение через ASGI transport httpx;
ASGI (Asynchronous Server Gateway Interface) — интерфейс между Python-сервером и приложением.
В unit-тестах доступность БД заменяется контролируемым результатом.
Реальный запуск ресурсов проверяется следующим набором.

## Интеграционные тесты

Интеграционный тест проверяет взаимодействие нескольких реальных компонентов.
Здесь используются настоящие PostgreSQL, asyncpg, SQLAlchemy, Alembic, FastAPI lifespan
и процессы вычислений, созданные через `spawn`. В 0.3.0 также используется настоящий Redis.
SQL-запросы не заменяются mock-объектами.
API-тесты отправляют сохранённые TLE и JSON, проверяют сериализованный WGS84-ответ
и ошибку SGP4, прошедшую границу процесса. Отдельный тест намеренно завершает реальный
вычислитель через `os._exit` и проверяет, что пул становится недоступным и закрывается.

Полностью в Docker:

```bash
docker compose --profile test run --build --rm tests
```

Или pytest в локальной `.venv`:

```bash
docker compose --profile test up -d --wait postgres-test redis-test
poetry run poe test-integration
```

Тесты используют только отдельный `postgres-test`. Его данные находятся в `tmpfs` — временном
хранилище в памяти — и исчезают после остановки контейнера. Рабочий volume не подключается.
Имя БД проверяется на суффикс `_test`, а реквизиты берутся исключительно из `APP_TEST_DB_*`.
В собственной конфигурации следует указывать выделенную тестовую БД: тесты создают и удаляют
служебную таблицу, очищают `users` и `satellites` и выполняют откат миграций.
Параллельные запуски на одной тестовой БД не предусмотрены.
Redis работает в отдельном контейнере без сохранения на диск, с отдельным портом и паролем.
Приложение тестов явно использует DB 15 и уникальный префикс для каждого теста, без очистки рабочего Redis.

| Сценарий | Что подтверждает |
| --- | --- |
| Upgrade → повторный upgrade → downgrade → upgrade | Миграции применимы, повторный запуск безопасен, исходная версия восстанавливается |
| `alembic check` | Применённая схема соответствует ORM metadata |
| Запрос готовности после lifespan | HTTP-обработчик действительно использует запущенную PostgreSQL |
| Успешная транзакция | Запись видна в следующей сессии после commit |
| Прикладная ошибка | Все записи операции откатываются |
| Нарушение уникальности | PostgreSQL отклоняет конфликт, транзакция откатывается, пул остаётся рабочим |
| Отмена асинхронной задачи | Незавершённая запись откатывается и соединение освобождается |
| Долгий SQL-запрос | Настроенный statement timeout срабатывает, после отката БД снова доступна |
| Вход и `/auth/me` | Проверяется настоящий Argon2-хеш; пароль и хеш не возвращаются |
| Смена пароля и отключение | Старые токены отклоняются до бизнес-операции |
| Параллельный POST с одинаковым NORAD ID | Одна запись и один `409`, без гонки предварительной проверки |
| Конфликт PUT | Исходные метаданные сохраняются после отката |
| Два Redis-клиента и 20 одновременных проверок | Общая квота ровно 5 допущенных запросов |
| Два токена пользователя, другой пользователь, истечение окна | Общая квота одного пользователя, независимость другого, восстановление доступа |
| Ошибки входа и недоверенный `X-Forwarded-For` | Все попытки одного адреса делят квоту |
| Недоступный Redis | Вход и защищённые операции закрываются, `ready=503`, `live=200` |

Для последующей работы можно остановить только тестовый контейнер:

```bash
docker compose --profile test stop postgres-test redis-test
```

## Проверка контейнерного приложения

```bash
./scripts/start-local.sh
curl --fail http://localhost:8000/health/ready
```

Эта проверка дополняет ASGI-тест: здесь используются собранный образ, настоящий HTTP-сервер,
TCP-соединение, сеть Compose и отдельный контейнер миграций.
При остановке PostgreSQL `/health/live` должен оставаться доступным, а `/health/ready`
должен вернуть 503 в пределах настроенного срока. После восстановления БД готовность должна восстановиться.

GitHub Actions повторяет проверки качества, интеграционные тесты и запуск Compose.
До push можно проверить конфигурацию и локальные эквиваленты; фактический запуск на GitHub произойдёт после публикации.

## С чего начинаются замеры

В 0.1.0 установлена исходная конфигурация: один HTTP-процесс, пять соединений в его DB-пуле,
ноль дополнительных соединений. Это начальные параметры, а не результат оптимизации.
В 0.2.0 добавлены ручные замеры ядра и HTTP с сохранением машиночитаемого отчёта.
Команды, начальные результаты и ограничения приведены в [замерах](benchmarks.md).

Первые входы: один КА, интервал один час и одни сутки, шаги 1 и 60 секунд.
Сначала измеряется один запрос, затем несколько одновременных запросов.
Для каждого опыта сохраняются исходные элементы, времена, версии, CPU/память Docker,
все влияющие переменные окружения и число повторов после прогрева.

Нужны полное время HTTP-ответа, время ядра, размер ответа, пик памяти,
доля отказов при перегрузке и задержка health API. Одно среднее значение может скрыть
редкие медленные запросы, поэтому сохраним медиану и p95 — время, быстрее которого завершились 95% запросов.
Доступность health API проверяется во время нагрузки, включая формирование большого JSON-ответа.

Затем меняется один параметр за опыт: число вычислительных процессов, число допущенных запросов
или размер входа. Начальный предел 100 000 точек сохраняется только если измерения подтвердят
приемлемые память и задержку. Изменение конфигурации документируется вместе с результатом.
До этих измерений численный SLA (Service Level Agreement — обязательство по уровню обслуживания)
для времени расчёта не заявляется.

## Проверка версии 0.1.0 — 20 октября 2026 года

- Ruff, ty и все pre-commit проверки прошли.
- Локально прошли 15 unit-тестов и 8 интеграционных тестов.
- В Linux-контейнере Python 3.13.14 прошли все 23 теста.
- Образы runtime/test собраны; PostgreSQL, мигратор и API запущены через Compose.
- Проверены HTTP 200 для live/ready, HTTP 503 для ready при остановленной БД и восстановление HTTP 200 после её запуска.
- Ответ ready при остановленной БД получен за 0.189 с. Это единичная проверка отказа, не бенчмарк производительности.
- GitHub Actions подготовлен; запуск на GitHub ожидает публикации репозитория.

## Проверка версии 0.2.0 — 20 октября 2026 года

- Образы приложения и тестов успешно собраны с Python 3.13.14.
- Первоначальный набор в Docker: 74 теста, из них 62 unit и 12 интеграционных на отдельной PostgreSQL.
- Локальная `.venv` отдельно выполнила 12 интеграционных тестов на тестовой БД.
- Проверены TLE/JSON через API, ошибки SGP4 между процессами и реальное аварийное завершение процесса.
- Compose применил существующую миграцию и запустил приложение с успешной readiness-проверкой.
- Численные тесты подтверждают реализацию выбранной модели, а не точность предсказания реального КА.
- Измерения ядра и полного HTTP-пути, включая перегрузку и health, описаны в [замерах](benchmarks.md).
- Четыре теста сначала воспроизвели HTTP 500 на `1e999`, `-1e999`, `NaN`, `Infinity`.
  Обработчик валидации исправлен: возвращаются только `loc`, `msg`, `type`, без отклонённого числа.
- Итоговый прогон Docker после исправлений: 79 тестов, из них 67 unit и 12 интеграционных.
- Проверены реальные HTTP-запросы обоих форматов, четыре числовые ошибки 422,
  превышение лимита точек и готовность PostgreSQL/пула через опубликованный порт.
- SHA-256 исходных файлов проверяется тестом; `.gitattributes` сохраняет CRLF и исходные пробелы
  после клонирования. Перед коммитом контрольные суммы также проверены у Git blobs.

## Проверка версии 0.2.1 — 20 октября 2026 года

- В Docker прошли 82 теста: 70 unit и 12 интеграционных на отдельной PostgreSQL.
- Unit-тесты проверяют, что оба примера из OpenAPI совпадают с запросами из `examples/`
  после нормализации времени и значений по умолчанию.
- Интеграционные тесты извлекают примеры из OpenAPI и отправляют их через настоящий
  пул процессов. Оба возвращают по 61 точке; проверяется также ошибка SGP4 между процессами.
- Контрольные численные тесты, отмена, тайм-ауты и авария процесса проходят с новым
  `OrbitCalculator`, `CalculationWorker` и Pydantic-моделью результата.
- Через опубликованный порт Docker выполнены оба примера Swagger и проверен ready версии 0.2.1.
- Бенчмарк в режиме `core` выполнен с одним повторением на каждый из четырёх сценариев.
  Новая модель отчёта прочитала как созданный отчёт, так и существующие core/HTTP-отчёты 0.2.0.
  Этот запуск проверяет работоспособность инструмента; исходная серия замеров 0.2.0 сохранена.

## Проверка версии 0.3.0 — 20 октября 2026 года

- В Docker прошёл 121 тест: 93 unit и 28 интеграционных на отдельных PostgreSQL и Redis.
- Проверены миграции в обе стороны, совпадение metadata, полный CRUD реестра,
  постраничная выдача, конкурентные дубликаты NORAD ID и откат конфликтующего PUT.
- Реальные вход и JWT проверяются перед API-тестами расчёта. Смена пароля и отключение
  пользователя отзывают старый доступ. Неверные подпись, назначение, типы и срок токена отклоняются.
- Два Redis-клиента совместно допускают ровно пять из двадцати конкурентных запросов.
  Проверены общая квота разных токенов одного пользователя, отдельная квота другого,
  восстановление после окна, лимит неудачных входов и отказ подключения Redis.
- Реальный `ConnectionRefusedError` PostgreSQL преобразуется в безопасный `503`.
  При отказе БД или Redis `ready=503`, `live=200`; внутренние исключения не возвращаются клиенту.
- Unit-тесты подтверждают общий deadline Redis и удержание памяти/места Argon2 после
  отмены ожидающего HTTP-запроса. Учётные данные benchmark не попадают в отчёт.
- Полный запуск выполнен через `start-local.sh`: рабочая PostgreSQL обновлена новой миграцией,
  CLI создал локального пользователя. В самом Swagger выполнены вход, Authorize и TLE-пример:
  `200`, 61 точка. Временная учётная запись UI-проверки затем отключена.
- HTTP-бенчмарк с авторизацией выполнен отдельно от тестов, по три повтора на сценарий.
  Результаты и границы интерпретации описаны в [замерах](benchmarks.md).
- Окончательный образ дополнительно проверен по TCP: оба примера из OpenAPI возвращают
  61 точку, метаданные проходят POST/GET/PUT/DELETE, запрос без токена получает `401`.
  В OpenAPI входа и реестра `422` описывает фактическую модель без отклонённого пароля.
