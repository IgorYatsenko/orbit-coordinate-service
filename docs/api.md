# Контракт API 1.0.0

`POST /api/v1/orbits/coordinates` принимает один аппарат и возвращает всю траекторию
в одном JSON-ответе. Расчёт не требует регистрации аппарата и не изменяет PostgreSQL.
Проверка пользовательского доступа обращается к PostgreSQL и Redis, затем отпускает
соединения до начала вычисления. Нужен Bearer-токен: [вход и ограничения](access.md).
Swagger UI на `/docs` содержит два готовых запроса в списке `Examples`: TLE и JSON.
После `Try it out` выбранный пример можно выполнить без изменения полей.
Элементы зафиксированы около собственной эпохи, поэтому пример работает независимо
от текущей даты и доступа к CelesTrak.

## Общая часть запроса

| Поле | Назначение |
| --- | --- |
| `orbit` | Объект одного из двух форматов ниже |
| `start`, `end` | ISO 8601 с явным часовым поясом, например `2026-10-20T05:01:00Z` |
| `step_seconds` | Целое число от 1 до 60; строки, дроби и boolean не принимаются |

Времена приводятся к UTC. Начало не должно быть позже конца.
В сетку попадают `start + k × step_seconds`, пока время не превышает `end`.
Если перевод часового пояса выводит дату за диапазон лет 1–9999, поле отклоняется через `422`.
При равных границах получается одна точка. Для суток с шагом 1 секунда получается
86401 точка, с шагом 60 секунд — 1441. Конец вне сетки отдельной точкой не добавляется.
Дробные секунды начала сохраняются. Входное значение секунды `60` не поддерживается:
сетка использует арифметику Python datetime, а не отдельную шкалу атомного времени.

Количество точек проверяется до передачи работы процессу. Начальный предел — 100000,
он задаётся `APP_COMPUTE_MAX_POINTS`. Дальность от эпохи искусственно не ограничивается;
качество прогноза нужно оценивать отдельно, см. [предметную область](domain.md).

## TLE

TLE (Two-Line Element Set) — две строки фиксированного формата, по 69 символов.
В объекте `orbit` задаются `format: "tle"`, `line1`, `line2` и необязательный `name`.
Пробелы внутри строк значимы. Строки передаются без перевода строки на конце.
Проверяются контрольные суммы, совпадение каталожных номеров, фиксированный формат
и допустимые диапазоны элементов. Поддерживаются числовые номера и Alpha-5.
Год эпохи из двух цифр трактуется по соглашению TLE: 57–99 → 1957–1999, 00–56 → 2000–2056.

Готовый запрос: [examples/request-tle.json](../examples/request-tle.json).

```bash
curl --fail-with-body -sS http://localhost:8000/api/v1/orbits/coordinates \
  -H 'Content-Type: application/json' --data-binary @examples/request-tle.json
```

## JSON с полями OMM

GP (General Perturbations) — орбитальные элементы из каталога CelesTrak.
OMM (Orbit Mean-Elements Message) определяет названия полей и их смысл.
В объекте `orbit` задаются `format: "omm"` и `elements`, содержащий один объект
из JSON-массива ответа CelesTrak. Это средние элементы для алгоритма SGP4.

Пример [examples/request-omm.json](../examples/request-omm.json) содержит полный запрос.
Поля элементов и единицы разобраны в [предметной области](domain.md).
`EPOCH` CelesTrak без смещения трактуется как UTC, как установлено форматом.
`CENTER_NAME=EARTH`, `REF_FRAME=TEME`, `TIME_SYSTEM=UTC`, `MEAN_ELEMENT_THEORY=SGP4`
можно не передавать. Если они переданы, значения должны совпадать.
Другие системы отсчёта и другие алгоритмы не принимаются. Неизвестные поля запрещены.

```bash
curl --fail-with-body -sS http://localhost:8000/api/v1/orbits/coordinates \
  -H 'Content-Type: application/json' --data-binary @examples/request-omm.json
```

JSON поддерживает NORAD ID от 1 до 999999999. В sgp4 2.27 внутренний идентификатор
ограничен Alpha-5: максимум 339999. Для больших номеров адаптер передаёт библиотеке
метку 0. Она не входит в уравнения движения. Настоящий номер сохраняется в модели
и возвращается в ответе; тест проверяет сохранение номера и равенство координат.
Такой адаптер позволяет использовать будущие каталожные номера без изменения физической модели.

## Ответ

| Поле | Значение |
| --- | --- |
| `norad_id` | Настоящий каталожный номер аппарата |
| `epoch` | Эпоха исходных элементов, UTC |
| `reference_frame` | `WGS84` |
| `start`, `end`, `step_seconds` | Нормализованные параметры запроса |
| `point_count` | Количество точек в массиве `points` |
| `points[].time` | Время конкретной точки, UTC |
| `points[].latitude_deg` | Геодезическая широта, градусы, от −90 до 90 |
| `points[].longitude_deg` | Долгота, градусы, от −180 до 180 |
| `points[].altitude_km` | Высота над эллипсоидом WGS84 в километрах |

Эпоха ответа сохраняет исходное значение; она не используется как дата запуска аппарата.
Значения координат не округляются до выбранного числа знаков.
Количество знаков в JSON не является обещанием физической точности.
Результат не зависит от доступности CelesTrak: все элементы передаёт клиент.

Заголовок `Server-Timing: compute;dur=...` показывает миллисекунды вычислений,
валидации результата и подготовки JSON внутри процесса. Он не включает ожидание,
передачу между процессами и по сети. Максимальный RSS процесса записывается в лог:
это наибольший объём его резидентной памяти за время жизни, включая предыдущие запросы.

## Ошибки

| HTTP | `detail.code` | Значение |
| --- | --- | --- |
| 422 | `detail`-массив с `loc`, `msg`, `type` | Ошибка типов, структуры, времени, контрольной суммы |
| 422 | `point_limit_exceeded` | Сетка превысила настроенный предел |
| 422 | `invalid_orbit` | Элементы нельзя преобразовать в поддерживаемую модель |
| 422 | `propagation_failed` | SGP4 или преобразование координат не смогли вычислить точку |
| 503 | `compute_busy` | Все допущенные места пула заняты |
| 503 | `compute_unavailable` | Пул ещё не готов или процесс аварийно завершился |
| 503 | `compute_timeout` | Истёк срок ожидания результата |

Ошибки расчёта имеют форму
`{"detail":{"code":"...","message":"...","time":null}}`.
При проблеме конкретной точки `time` содержит её UTC-время. Ошибка любой точки
завершает весь запрос: неполная траектория не возвращается. NaN и бесконечности запрещены.

Валидационные ошибки сохраняют форму списка FastAPI, но возвращают только путь поля,
сообщение и тип ошибки. Отклонённое значение и внутренний контекст не копируются в ответ.
Это позволяет корректно вернуть `422` даже при переполненном числе вроде `1e999`,
которое стандартный JSON-обработчик не смог бы сериализовать обратно как конечное число.

Отмена ожидающей задачи и тайм-аут не прерывают уже выполняющийся процесс.
Его место остаётся занятым до действительного завершения работы. Бесконечная очередь
новых запросов не создаётся. Клиент может повторить запрос после `503` с выбранной им задержкой.

## Живость и готовность

- `/health/live` проверяет отзывчивость HTTP-процесса без обращения к ресурсам.
- `/health/ready` параллельно проверяет PostgreSQL и вычислительный пул.
- Дополнительно проверяется Redis: он необходим для допуска бизнес-запросов.
- При свободном месте пул получает короткую пробу с ограниченным временем ожидания.
  Одновременные health-запросы разделяют одну пробу.
- Если все процессы выполняют расчёты, работающий пул считается готовым.
  Перегрузка выражается через `503` расчёта. Зависшая health-проба остаётся неуспешной.
- Аварийное завершение процесса делает пул недоступным; для восстановления требуется
  перезапуск приложения. Автоматическая пересборка пула не добавлена в прототип.

`ready` возвращает поля `status`, `version`, `database`, `compute`, `redis` и HTTP 200 либо 503.
Численное ядро не использует БД; общий статус готовности относится ко всему микросервису,
включая авторизацию и реестр. Health API не требует токена и не расходует квоту пользователя.

## Пользовательский доступ

| Маршрут | Результат |
| --- | --- |
| `POST /api/v1/auth/login` | JSON с `username`, `password` → токен, тип и срок действия |
| `GET /api/v1/auth/me` | `id`, `username`, `is_active`, `created_at` текущего пользователя |

Отсутствующий, неверный, просроченный или отозванный токен даёт `401 unauthorized`
с заголовком `WWW-Authenticate: Bearer`. Неизвестный логин, неверный пароль и отключённая
учётная запись имеют одинаковый ответ. При превышении квоты: `429 rate_limit_exceeded`
и `Retry-After`. При отказе лимитера: `503 rate_limiter_unavailable`; при занятости
проверок пароля: `503 authentication_busy`; при ошибке операции с БД: `503 database_unavailable`.
Форма общих ошибок: `{"detail":{"code":"...","message":"..."}}`.
Ошибки не включают пароль, токен, SQL или параметры подключения.

## Реестр метаданных

Все маршруты требуют пользовательского токена и работают с общим реестром.

| Метод и маршрут | Результат |
| --- | --- |
| `POST /api/v1/satellites` | `201`, созданная запись |
| `GET /api/v1/satellites` | `200`, страница списка |
| `GET /api/v1/satellites/{id}` | `200`, запись по внутреннему UUID |
| `PUT /api/v1/satellites/{id}` | `200`, полностью заменённые метаданные |
| `DELETE /api/v1/satellites/{id}` | `204`, пустое тело |

Тело создания и замены:

```json
{"norad_id":25544,"name":"ISS (ZARYA)","international_designator":"1998-067A","launch_date":"1998-11-20"}
```

`norad_id` целый 1–999999999, уникален; `name` содержит 1–200 символов после удаления
пробелов по краям. `international_designator` необязателен, 1–32 символа либо `null`;
`launch_date` необязательна, календарная дата либо `null`, предоставляется клиентом.
Дата не выводится из эпохи элементов. Неизвестные поля отклоняются.
Ответ дополнительно содержит `id` (UUID), `created_at`, `updated_at` (UTC).
UUID является внутренним неизменяемым идентификатором, NORAD ID можно исправить через PUT.

PUT заменяет все метаданные: пропущенные необязательные поля становятся `null`.
Одновременные изменения одной записи применяются по порядку фиксации транзакций;
версии записи для условного обновления нет. Повторный NORAD ID даёт `409 satellite_conflict`,
отсутствующая запись при чтении, замене или удалении: `404 satellite_not_found`.
Уникальность обеспечивает PostgreSQL, включая одновременные запросы.
Ошибочная замена откатывается целиком.

Список отсортирован по возрастанию NORAD ID. `limit` по умолчанию 50, допустим 1–200;
`after_norad_id` по умолчанию 0. Ответ: `{"items":[...],"next_after_norad_id":25544}`.
Для следующей страницы передайте возвращённое значение как `after_norad_id`.
`null` означает, что в текущем запросе продолжения не было. Общего `total` нет, чтобы
не считать весь реестр на каждой странице. Между запросами список отражает текущее состояние:
создание, удаление и изменение NORAD ID могут менять состав последующих страниц.
Это не зафиксированный снимок всей БД на момент первой страницы.

Расчёт не читает орбиту из реестра, не создаёт и не обновляет метаданные автоматически.
TLE, JSON элементов, история траекторий и результаты вычисления в PostgreSQL не сохраняются.
