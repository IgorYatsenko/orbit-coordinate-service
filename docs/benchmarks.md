# Замеры 0.2.0 и 0.3.0

Это начальная проверка конфигурации, а не обязательство по нагрузке.
Фиксируем конкретные входные элементы, зависимости и оборудование, чтобы изменения можно
было сравнивать. Физическая точность прогноза здесь не измеряется.

## Как воспроизвести

Нужны установленное Poetry-окружение и работающий API для HTTP-режима:

```bash
docker compose up --build --wait
poetry run poe add-test-user
APP_BENCH_MODE=core APP_BENCH_OUTPUT=artifacts/core.json poetry run poe benchmark
APP_BENCH_MODE=http APP_BENCH_OUTPUT=artifacts/http.json poetry run poe benchmark
```

Перед HTTP-замером выполните `poetry run poe add-test-user`
и проверьте `APP_BENCH_USERNAME` и `APP_BENCH_PASSWORD` в локальном `.env`.
Пара из `.env.example` совпадает с демонстрационными `testuser / test-password`.
Один вход выполняется перед прогревом; его время не включается в сценарии расчёта.
Пользователь и пароль исключены из отчёта. Квота пользователя действует как обычно;
стандартный прогон с пятью повторами и всплеском из четырёх запросов помещается в 60 запросов.
При повторении подряд учитывайте уже израсходованное окно.
Таблицы ниже относятся к первоначальному прогону 0.2.0 без авторизации;
новый прогон нужно сохранять отдельно и не выдавать старые числа за результат 0.3.0.

Замер одного размера порции выполняется отдельным процессом:

```bash
APP_COMPUTE_CHUNK_POINTS=1024 APP_BENCH_MODE=core \
  APP_BENCH_OUTPUT=artifacts/core-1024.json poetry run poe benchmark
```

Для сравнения повторить с 4096 и 16384. Во время измерения не запускать другие бенчмарки,
тесты или сборки. Для HTTP-замера настройки окружения benchmark должны соответствовать
настройкам запущенного приложения: отчёт фиксирует локальное окружение клиента,
а не опрашивает конфигурацию удалённого сервера.

Вход — `examples/request-omm.json`, МКС, эпоха 2026-10-20T05:01:14.050560Z.
Сценарии используют начало примера, длительность 1/24 часа и шаг 1/60 секунд.
Проводится один прогрев одной точкой, затем по пять повторений на сценарий.
HTTP-режим дополнительно отправляет четыре суточных запроса одновременно и опрашивает
`live`/`ready`. Результаты и подробные отдельные измерения сохраняются в игнорируемый `artifacts/`.
В отчёт входят UTC-время, версии, платформа, число CPU, настройки, SHA-256 запроса,
статусы, время, размер ответа и результаты health-проверок.

Медиана — центральное значение пяти измерений. Указанный p95 вычисляется ближайшим
рангом; при пяти измерениях это максимум. Такой объём данных подходит для первого сравнения,
но недостаточен для обещаний хвостовой задержки под устойчивой нагрузкой.

`compute` включает численную работу, построение типизированного результата и JSON.
HTTP дополнительно включает передачу между процессами, отправку и чтение всего тела.
Клиент не разбирает большой JSON во время измерения, чтобы не блокировать собственные health-пробы.
Резидентная память измеряется через `getrusage().ru_maxrss`: максимум процесса за время его жизни,
включая импорты, предыдущие сценарии и повторения. Это не разница памяти до и после запроса.
Она не равна памяти всего приложения с HTTP-процессом и несколькими вычислителями.

## Сравнение порций на локальной машине

20 октября 2026 года: macOS 27.0.1, ARM64, 8 логических CPU; Python 3.13.14,
Skyfield 1.55, sgp4 2.27 с C++-ускорением, NumPy 2.5.4. Один прямой процесс расчёта,
один native-поток. Каждый размер порции измерялся новым процессом.

| Точек в порции | Сутки, шаг 1 с: медиана, мс | Максимальный RSS процесса, МиБ |
| --- | ---: | ---: |
| 1024 | 1428.13 | 200.47 |
| 4096 | 1532.38 | 392.08 |
| 16384 | 1648.30 | 797.53 |

Меньшая порция здесь сократила память временных массивов Skyfield и не ухудшила время.
Поэтому `APP_COMPUTE_CHUNK_POINTS=1024` выбран начальным значением. Это не доказательство
оптимальности на любом CPU или для всех орбит. Число процессов пока оставлено равным двум;
дальнейший подбор зависит от доступных CPU, памяти и реальной конкуренции запросов.

| Интервал / шаг | Точки | Ядро и JSON: медиана, мс | Объём ответа, байт |
| --- | ---: | ---: | ---: |
| 1 ч / 60 с | 61 | 1.29 | 8280 |
| 1 ч / 1 с | 3601 | 54.09 | 477950 |
| 24 ч / 60 с | 1441 | 23.95 | 191961 |
| 24 ч / 1 с | 86401 | 1428.13 | 11503348 |

Большой ответ занимает около 11.5 MB до сжатия; передача и память результата остаются
существенной частью стоимости даже при быстром SGP4. Начальный предел 100000 точек
сохранён как инженерное ограничение. Увеличение предела требует отдельной проверки памяти
нескольких процессов и времени полного ответа.

## Полный HTTP-путь в Docker

Docker предоставляет 6 CPU и 6210306048 байт памяти всей виртуальной машине.
Отдельного memory limit у контейнера приложения нет. Приложение работает в Linux
на Python 3.13.14: один HTTP-процесс, два вычислителя, порция 1024, один native-поток.
Клиент benchmark работает на macOS через опубликованный localhost-порт.

| Интервал / шаг | HTTP: медиана, мс | HTTP: p95, мс | `compute` внутри процесса: медиана, мс |
| --- | ---: | ---: | ---: |
| 1 ч / 60 с | 7.69 | 45.31 | 4.41 |
| 1 ч / 1 с | 227.04 | 276.71 | 217.49 |
| 24 ч / 60 с | 129.43 | 165.97 | 122.75 |
| 24 ч / 1 с | 5243.52 | 5416.61 | 5040.02 |

Размер суточного ответа здесь составил 11503666 байт. Побитовое равенство последних
цифр численного результата и длины JSON между разными средами не обещается;
численные тесты проверяют одинаковые допуски.
Прямые числа macOS и HTTP в Docker нельзя трактовать как замер одной только цены HTTP:
это разные среды выполнения. Для оценки передачи здесь нужно сравнивать HTTP и `compute`
внутри одного Docker-запроса.

В серии из четырёх одновременных суточных запросов два получили 200 и два — 503.
Медиана успешных ответов — 5461.58 мс, максимум — 5477.22 мс.
Во время всех сценариев выполнено по 561 запросу `live` и `ready`, все вернули 200.
Максимум времени `live` — 39.23 мс, `ready` — 206.07 мс.
Это наблюдение одной короткой серии; устойчивый поток запросов и медленные клиенты
требуют самостоятельного нагрузочного замера перед подбором ресурсов для эксплуатации.

## HTTP с авторизацией и Redis, версия 0.3.0

Замер 20 октября 2026 года, `2026-10-20T16:22:12Z`. Клиент на macOS 27.0.1 ARM64,
Python 3.13.14, 8 логических CPU. API в той же Docker VM: 6 vCPU, 6210306048 байт памяти.
Отдельный лимит памяти контейнера API не задан. Один HTTP-процесс, два вычислителя,
порция 1024, один численный поток. Skyfield 1.55, sgp4 2.27, NumPy 2.5.4,
PyJWT 2.15.1, argon2-cffi 25.1.0, redis-py 8.1.0; сервер Redis 8.10.2.
Пароль проверяется один раз при входе; каждый измеряемый запрос проверяет подпись,
пользователя в PostgreSQL и квоту Redis. Использованы стандартные 60 запросов/60 секунд.
Во время измерения не запускались сборки и тесты. Отчёт: локальный `artifacts/http-0.3.0.json`.

```bash
APP_BENCH_MODE=http APP_BENCH_REPETITIONS=3 \
  APP_BENCH_OUTPUT=artifacts/http-0.3.0.json poetry run poe benchmark
```

| Интервал и шаг | Точек | HTTP, медиана, мс | Максимум трёх, мс | Вычисление внутри запроса, медиана, мс |
| --- | ---: | ---: | ---: | ---: |
| 1 час, 60 с | 61 | 24.71 | 37.85 | 8.22 |
| 1 час, 1 с | 3601 | 274.28 | 323.19 | 239.37 |
| 24 часа, 60 с | 1441 | 88.50 | 115.88 | 81.05 |
| 24 часа, 1 с | 86401 | 5406.22 | 5522.23 | 5109.91 |

Суточный ответ с шагом 1 с: 11503666 байт. Всплеск четырёх суточных запросов:
два ответа `200`, два `503`; медиана успешных 5547.18 мс, максимум 5569.13 мс.
Выполнено по 381 запросу live и ready, все `200`. Максимум live 24.86 мс,
ready 334.69 мс. Три повтора показывают работоспособность пути с контролем доступа,
но не отделяют его стоимость от колебаний времени Docker и не гарантируют хвостовую задержку.
Для оценки цены авторизации нужен отдельный парный эксперимент с одинаковым окружением.

Отдельно, после сборки окончательного образа, проверены три последовательных входа
с настоящей проверкой пароля: медиана 144.29 мс. Использованы Argon2id 64 MiB,
три прохода, две полосы. Локальный отчёт `artifacts/access-0.3.0.json` сохраняет времена
и ready без логина, пароля или токена. Это проверка выбранной стартовой настройки,
нагрузка множества одновременных входов здесь не измерялась.
