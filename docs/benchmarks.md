# Замеры

Приведены замеры 1.0.0 от 20 октября и 1.1.0 от 21 октября 2026 года.
Это проверка демонстрационной конфигурации;
обязательство по времени ответа при длительной нагрузке не задаётся. Точность положения
реального спутника этими опытами не измеряется.

## Условия и методика 1.0.0

Ядро и API работают в одной Docker VM: Linux ARM64, 6 CPU, 6210306048 байт памяти
на всю VM, Docker Engine 29.8.2. Отдельный memory limit контейнера API не задан.
Python 3.13.14, Skyfield 1.55, sgp4 2.27, NumPy 2.5.4; зависимости зафиксированы lock-файлом.
HTTP-клиент работает на macOS ARM64 через опубликованный localhost-порт.
Во время каждого замера не запускаются другие бенчмарки, сборки или тесты.

Вход — `examples/request-omm.json`, МКС, эпоха `2026-10-20T05:01:14.050560Z`.
После прогрева одной точкой выполняются следующие сценарии:

| Интервал / шаг | Точек |
| --- | ---: |
| 1 час / 60 с | 61 |
| 1 час / 1 с | 3601 |
| 24 часа / 60 с | 1441 |
| 24 часа / 1 с | 86401 |
| Предел `APP_COMPUTE_MAX_POINTS` / 1 с | 100000 |

Ядро: три повтора каждого сценария, один прямой процесс, отдельный контейнер на размер порции.
HTTP: пять повторов, затем четыре одновременных запроса по 100000 точек;
параллельно опрашиваются `/health/live` и `/health/ready` с паузой 0,05 с.
HTTP-запросы проходят проверку токена, пользователя в PostgreSQL и квоты Redis.
Вход выполняется один раз до прогрева и не включён в измеряемое время расчётов.

`compute` включает математику, построение моделей и JSON. HTTP дополнительно включает
проверки доступа, передачу между процессами и чтение клиентом всего тела ответа.
Клиент не разбирает большой JSON во время измерения, чтобы не задерживать собственные health-пробы.
Медиана — центральное измерение. p95 вычисляется ближайшим рангом; при трёх или пяти
повторах это максимум серии, а не достоверная оценка редких задержек длительной нагрузки.

Память ядра — максимальный RSS (Resident Set Size, память процесса в оперативной памяти)
за всё время его жизни через `getrusage`, включая импорты и предыдущие сценарии.
Для API дополнительно читается `memory.peak` всей группы процессов контейнера Linux cgroup v2.
Это разные способы учёта: значение контейнера включает также кэш и не равно сумме пиков RSS.

## Как повторить текущую версию

Подготовка описана в [README](../README.md#quick-start). Используйте `.env.example`
как исходную конфигурацию. Для клиента замеров установите локальную среду Python 3.13
и Poetry из раздела разработки README. Демонстрационный запуск API использует только Docker.
Для HTTP нужны работающий API и демопользователь:

```bash
docker compose up --build --wait
docker compose exec app python -m api.demo_user
APP_BENCH_MODE=http APP_BENCH_OUTPUT=artifacts/http.json poetry run poe benchmark
```

В `.env.example` уже указаны `APP_BENCH_USERNAME=testuser` и `APP_BENCH_PASSWORD=test-password`.
Логин и пароль исключены из отчётов. Текущий сценарий также включает двое суток с шагом
1 секунда. Один стандартный HTTP-прогон расходует 35 запросов
из квоты 60; при повторениях учитывайте текущую квоту и `Retry-After`.

Сравнение ядра в Docker, без запуска тестовых БД:

```bash
mkdir -p artifacts
docker compose --profile test build tests
docker compose --profile test run --rm --no-deps \
  -e APP_BENCH_MODE=core -e APP_COMPUTE_WORKERS=1 \
  -e APP_COMPUTE_CHUNK_POINTS=1024 -e APP_BENCH_REPETITIONS=3 \
  -e APP_BENCH_OUTPUT=artifacts/core-1024.json \
  --volume "$PWD/artifacts:/app/artifacts" tests poetry run poe benchmark
```

Повторите последнюю команду с 512 и 4096, изменив также имя отчёта.
Каждый запуск создаёт новый процесс, поэтому пик памяти не переносится между конфигурациями.
Для сравнения вычислителей через HTTP:

```bash
APP_COMPUTE_WORKERS=1 docker compose up -d --wait app
APP_COMPUTE_WORKERS=1 APP_BENCH_MODE=http \
  APP_BENCH_OUTPUT=artifacts/http-w1.json poetry run poe benchmark
APP_COMPUTE_WORKERS=2 docker compose up -d --wait app
APP_COMPUTE_WORKERS=2 APP_BENCH_MODE=http \
  APP_BENCH_OUTPUT=artifacts/http-w2.json poetry run poe benchmark
```

Меняется только число вычислителей. Остальные настройки клиента должны совпадать с API:
отчёт фиксирует локальное окружение клиента, а не опрашивает конфигурацию сервера.
В измеренной среде максимум памяти контейнера читается так:

```bash
docker compose exec -T app cat /sys/fs/cgroup/memory.peak
```

JSON-отчёты сохраняют UTC-время, версии, платформу, CPU, SHA-256 входа, настройки,
все отдельные времена, статусы и health-пробы. Локальные отчёты находятся в `artifacts/`,
исключённом из Git; результаты прошлых версий доступны по тегам.

## Размер порции

| Точек в порции | 1 час / 1 с, медиана, мс | 24 часа / 1 с, медиана, мс | 100000 точек, медиана, мс | Пик RSS процесса, МиБ |
| --- | ---: | ---: | ---: | ---: |
| 512 | 226.03 | 5129.66 | 5869.26 | 202.31 |
| 1024 | 217.67 | 5113.64 | 6479.84 | 202.29 |
| 4096 | 430.97 | 5440.32 | 5836.61 | 281.92 |

Оставлено `APP_COMPUTE_CHUNK_POINTS=1024`: в сценариях часа и суток оно оказалось
быстрее, а 512 не уменьшило пик памяти. Порция 4096 быстрее в максимальном запросе,
но расходует больше памяти и заметно медленнее в часовом сценарии. Это сбалансированный
выбор по короткой серии, а не доказательство глобального оптимума.

Отчёты: `artifacts/core-1.0.0-c512.json`, `core-1.0.0-c1024.json`, `core-1.0.0-c4096.json`.

## Полный HTTP-путь

Один HTTP-процесс, два вычислителя, порция 1024, один численный поток на вычислитель.
В каждом последовательном сценарии все пять ответов получили `200`.

| Интервал / шаг | HTTP, медиана, мс | HTTP, максимум пяти, мс | `compute`, медиана, мс |
| --- | ---: | ---: | ---: |
| 1 час / 60 с | 19.13 | 91.92 | 6.98 |
| 1 час / 1 с | 321.45 | 397.17 | 294.92 |
| 24 часа / 60 с | 116.58 | 167.89 | 103.60 |
| 24 часа / 1 с | 7154.33 | 7980.16 | 6618.32 |
| 100000 точек / 1 с | 6782.13 | 8772.80 | 6538.20 |

Ответ на 100000 точек занимает 13315153 байта, около 12,70 МиБ без сжатия.
Время не растёт идеально пропорционально размеру: короткие серии на общей Docker VM
заметно колеблются. Меньшее число точек не гарантирует меньшую измеренную медиану.

| Вычислителей | 100000 точек последовательно, медиана, мс | Ответы во всплеске четырёх запросов | Медиана успешных во всплеске, мс | Пик памяти API-контейнера, МиБ |
| --- | ---: | --- | ---: | ---: |
| 1 | 6801.35 | 1 × 200, 3 × 503 | 6146.03 | 267.24 |
| 2 | 6782.13 | 2 × 200, 2 × 503 | 7141.04 | 384.02 |

Два вычислителя позволяют рассчитывать две независимые траектории одновременно.
Каждый отдельный запрос выполняется одним процессом. Дополнительный расход памяти
в этой серии составил около 117 МиБ. Большее число процессов отдельно не измерялось.

| Вычислителей | Успешных проб каждого health endpoint | Максимум live, мс | Максимум ready, мс |
| --- | ---: | ---: | ---: |
| 1 | 1409 из 1409 | 195.79 | 330.98 |
| 2 | 1243 из 1243 | 209.02 | 465.17 |

Все последовательные расчёты и health-пробы успешны в обеих конфигурациях.
Первая серия с одним вычислителем обнаружила ложный отказ из-за health-пробы;
после исправления и регрессионного теста серия повторена. Итоговые таблицы используют
повторный замер. Записи завершения отчётов: `2026-10-20T19:09:28Z` и `19:15:02Z`.
Отчёты: `artifacts/http-1.0.0-w1-c1024.json`, `http-1.0.0-w2-c1024.json`;
память: `artifacts/memory-1.0.0-w1.txt`, `memory-1.0.0-w2.txt`.

## Выбранная конфигурация 1.0.0 и ограничения

- `APP_HTTP_WORKERS=1`: HTTP-процесс сохранял отзывчивость под измеренной нагрузкой.
  Каждый дополнительный HTTP-процесс создавал бы собственные пулы и расходовал память.
- `APP_COMPUTE_WORKERS=2`: два одновременных тяжёлых расчёта при измеренном пике
  API-контейнера 384 МиБ укладываются в выделенную Docker VM.
- `APP_COMPUTE_CHUNK_POINTS=1024`: баланс результатов сравнения порций выше.
- `APP_COMPUTE_NUMERIC_THREADS=1`: фиксирует число численных потоков на процесс
  и предотвращает их неявное умножение. Другие значения отдельно не сравнивались.
- `APP_COMPUTE_MAX_POINTS=100000`: включает сутки с шагом в секунду и ограничивает
  большой ответ. Измерены два одновременных запроса на этом пределе; 100001 точка отклоняется через `422`.
- `APP_COMPUTE_TIMEOUT_SEC=30`: оставляет запас относительно наблюдавшихся времён.
  Для другого оборудования значение задаётся окружением.

Эти значения зафиксированы для 1.0.0; дальнейшее увеличение предела описано ниже.
Проверены короткие серии;
длительная нагрузка, медленные клиенты, много одновременных входов и нагрузка на реестр
не измерялись. Рост числа пользователей и HTTP-процессов требует нового замера памяти
всего окружения, включая PostgreSQL, Redis и проверки паролей.

## Увеличенный предел 1.1.0

21 октября 2026 года проверено отдельное окружение Compose с новой БД и портом API
18081. Условия: Docker Engine 29.8.2, Linux ARM64, 6 CPU, 6210306048 байт памяти
на всю VM, Python 3.13.14 и те же зафиксированные версии Skyfield, sgp4 и NumPy.
Отдельный memory limit API не задан. Клиент работает на macOS через опубликованный порт.
Исходный запрос — тот же `examples/request-omm.json`; SHA-256 сохранён в отчётах.

Конфигурация: один HTTP-процесс, два вычислителя, порции по 1024 точки,
один численный поток на процесс, предел 200000 точек. После прогрева выполнены
три последовательных повтора каждого сценария и четыре одновременных запроса на пределе.
Одновременно опрашивались оба health-endpoint с паузой 0,05 с.

| Сценарий | Точек | Медиана HTTP, мс | Максимум трёх повторов, мс |
| --- | ---: | ---: | ---: |
| 1 час / 60 с | 61 | 33.05 | 54.02 |
| 1 час / 1 с | 3601 | 278.75 | 305.49 |
| 24 часа / 60 с | 1441 | 116.56 | 175.66 |
| 24 часа / 1 с | 86401 | 5654.89 | 5729.80 |
| 48 часов / 1 с | 172801 | 11501.19 | 11520.62 |
| Предел / 1 с | 200000 | 12123.87 | 13423.62 |

Во всплеске два запроса завершились `200`, два получили `503 compute_busy`.
Медиана успешных ответов — 13402.28 мс, максимум — 13479.75 мс.
Ответ на 200000 точек занимает 26632031 байт без сжатия.
Пик памяти всей группы процессов API — 649703424 байта, около 619,61 МиБ.

Для каждого health-endpoint получено 1689 ответов, все `200`.
Медиана / максимум задержки: live — 5.55 / 114.56 мс, ready — 6.44 / 265.82 мс.

Первый прогон с прежним ожиданием 30 секунд также сохранён: последовательные запросы
прошли, во всплеске были два быстрых `503` и два `503` после истечения срока ожидания.
В этом прогоне наблюдались значительные колебания даже на малых запросах; их причина
не установлена. Результаты не используются для утверждений об ускорении между версиями.
Повторный прогон с ожиданием 60 секунд дал результаты таблицы выше.

Зафиксированы `APP_COMPUTE_MAX_POINTS=200000`, `APP_COMPUTE_TIMEOUT_SEC=60`
и `APP_BENCH_TIMEOUT_SEC=90`. Предел включает двое суток с шагом 1 секунда;
ожидание даёт запас на наблюдавшиеся колебания. Число вычислителей и размер порции
сохранены по результатам предыдущих сравнений. Эти короткие серии не гарантируют
время ответа при другой нагрузке или на другом оборудовании.

Отчёты: `artifacts/http-1.1.0-w2-c1024-t30.json` и `http-1.1.0-w2-c1024-t60.json`.
Новые отчёты содержат `error_code`, различая занятость пула и тайм-аут.
Повторить текущую конфигурацию после quick start и установки локальной среды разработки:

```bash
APP_BENCH_MODE=http APP_BENCH_REPETITIONS=3 \
  APP_BENCH_OUTPUT=artifacts/http-1.1.0.json poetry run poe benchmark
```
